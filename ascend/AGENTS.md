# Ascend implementation instructions

For BznsFlow work, follow the parent repository instructions and canonical Operating-System routing.

Before implementation, read [the project engineering pack](implementation/engineering-pack.md), [shared foundation](implementation/shared-foundation.md), [build queue](implementation/README.md) and [agent runbook](implementation/agent-runbook.md). Then read the selected sector's implementation file and its original product specification. They are a single requirement set.

Build one selected task at a time. Reuse completed foundation work, existing domain authority, authenticated API/Convex boundaries and shared six-tab UI. Preserve unrelated edits. A source-inspected or proposed file is not an implemented feature.

Maintain a requirement → implementation → automated assertion map and dated task evidence under implementation/evidence/. Never mark a control verified without its actual result. Keep synthetic, isolated-backend and production evidence separate.

Testing remains automated-only with fake transports and synthetic data. The documentation request grants no production deployment, customer sends, ad spending, credential changes or migrations. Determine any later authorization from the current user task; do not request permission for ordinary reversible local work already authorized.

Runtime changes outside this folder still inherit repository engineering skills and review requirements. No extra primary tabs: Ascend has Chats, sector Work, Customers, Broadcasts, Insights and Settings; preserve Catalyst's existing four-tab behavior.
