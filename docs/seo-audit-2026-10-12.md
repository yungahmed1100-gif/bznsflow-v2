# BznsFlow SEO audit — 12 October 2026

## Executive assessment

The public site's technical indexing foundation is sound in the tested sample. All 10 sitemap URLs return 200, contain meaningful initial HTML, permit indexing, and have localized metadata and self-referencing canonicals. Arabic and English alternates are present. No blocking indexing defect was identified; this does **not** establish that Google has indexed the pages.

The largest growth opportunity is search-focused content for the current Catalyst offer. The site exposes only two marketing page types per language: the homepage and the playbook landing page. Six of the ten sitemap URLs are legal pages. There is also a confirmed broken social preview image, weak navigation to supporting pages, and homepage performance that warrants investigation.

| Priority | Finding | Impact | Effort |
| --- | --- | --- | --- |
| P1 | Search coverage is concentrated on the homepage; no dedicated public Catalyst/channel/use-case pages in the audited set | High potential organic acquisition impact; demand not quantified | Medium–large |
| P1 | Homepage lab sample: Arabic LCP 3.76s; English CLS 0.1855 | Potential user experience and search impact; field performance unknown | Diagnose first |
| P2 — quick win | Shared social preview image returns 404 | Broken image previews on shared links; not a demonstrated ranking defect | Small |
| P2 — quick win | Playbook, terms and deletion pages have no anchor-link path from either homepage in the crawled public graph | Discovery, navigation and trust | Small |
| P2 | Playbook title/content does not clearly answer a specific search need | Limited informational search opportunity | Medium |
| P3 | Homepage language navigation uses buttons rather than links | Weaker crawlable navigation; hreflang already mitigates discovery | Small |

This was an audit. No application code, production configuration, forms, messages or deployments were changed. Existing Ascend and route edits were preserved.

## Technical findings

### T1. Homepage performance needs measured diagnosis — P1

**Evidence:** the existing desktop crawler measured:

| Page | LCP | CLS | FCP | TTFB |
| --- | --- | --- | --- | --- |
| Arabic `/` | 3,760ms | 0.0142 | 3,760ms | 435ms |
| English `/en` | 468ms | 0.1855 | 468ms | 113ms |

**Impact:** potential usability and search performance risk. These are single, unthrottled desktop observations, not mobile Lighthouse scores or field Core Web Vitals. INP was not measured. The difference between locales does not establish that Arabic is inherently slower.

**Fix:** record cold mobile and desktop performance traces for both pages, including layout-shift attribution and the LCP element. Inspect `src/root.jsx:38` and its blocking Google Fonts stylesheet, font metric changes, hero transitions in `src/components/sections/HeroSection.jsx` and `src/styles/hero.css`, and initial chat loading. Treat these as investigation targets, not proven causes. Stabilize measured shifting elements and reduce critical font work where traces support it.

Right-size the main logo and chat avatar as a low-cost asset improvement: the homepage logo is 500px wide for a 60px desktop box (44,191 bytes), and the avatar is 256px for a 64px box (72,863 bytes). Preserve adequate high-density resolution and explicit dimensions; compare optimized WebP/AVIF or smaller PNG output visually. The small client logos total little data individually; their pixel-ratio warnings are lower priority.

**Acceptance:** repeat comparable cold runs after fixes; report median and variability, not the best run. Check field data when available. The good field thresholds are LCP ≤2.5s, INP ≤200ms, CLS ≤0.1 at the 75th percentile. [Web Vitals guidance](https://web.dev/articles/vitals).

### T2. Shared Open Graph/Twitter image is missing — P2

**Evidence:** `src/components/ui/Seo.jsx:9` defaults to `https://www.bznsflowai.com/og-image.jpg`. All ten public pages advertise this image. Two independent HTTP checks returned **404**, with `text/html` rather than an image. There is no corresponding file in `public/`.

**Impact:** social preview reliability and click appeal. This does not block page indexing.

**Fix:** supply an approved 1200 × 630 preview at `public/og-image.jpg`, or point the shared metadata to an actual equivalent asset. Keep `src/root.jsx` dimensions and alt text accurate. A localized pair can follow if useful, but a working shared asset is the immediate repair.

**Acceptance:** the advertised absolute URL returns 200 and the expected image MIME type; dimensions match; inspect the rendered `og:image` and `twitter:image` on both locales and refresh social preview caches after an authorized release. Extend the audit to fetch advertised preview assets: its current presence-only check missed this defect.

### T3. Supporting pages are disconnected from homepage navigation — P2

**Evidence:** breadth-first traversal from both homepages through initial-HTML links reaches the home and privacy pairs, but not `/playbook`, `/terms`, `/data-deletion` or their English equivalents. The rendered homepage anchor lists likewise contain no links to these destinations. The playbook pair links to each other and back to the site, and is in the sitemap; it is not entirely undiscoverable.

**Impact:** reduces user discovery and contextual internal linking. Terms/deletion accessibility also supports trust.

**Fix:** in `src/components/layout/Footer.jsx`, add localized Terms and Data deletion links beside Privacy. Add a normal, descriptive link to the playbook from a relevant homepage section or resource navigation. Keep the primary audit CTA prominent. Do not rely solely on the exit-intent form to expose the resource.

**Acceptance:** a visitor and a crawler starting on each homepage can reach all intended public support/resource pages through `<a href>` links, without submitting a form or triggering exit intent. Google recommends links to important pages from other site pages. [Link guidance](https://developers.google.com/search/docs/crawling-indexing/links-crawlable).

### T4. Homepage language destinations are button-only — P3

**Evidence:** `src/components/layout/NavBar.jsx` renders language choices as buttons calling `onSetLanguage`; `src/pages/Home.jsx:90` navigates programmatically. The homepage has no direct language-alternate anchor. Legal and playbook pages already use language links.

**Impact:** a navigation improvement, not an indexing blocker: the sitemap and head hreflang already expose the alternates.

**Fix:** render the language choices as real links to `/` and `/en`; preserve preference recording, focus handling and current-language semantics without depending on JavaScript for the destination.

**Acceptance:** both destinations appear as anchors in initial HTML; navigation still works with JavaScript disabled; the menu remains keyboard usable. Preserve self-canonicals and reciprocal hreflang. Arabic at the unprefixed root is valid and does not require a URL migration. [Localized-page guidance](https://developers.google.com/search/docs/specialty/international/localized-versions).

## On-page and content findings

### C1. Too few pages address distinct buyer questions — P1

**Evidence:** `src/routes-manifest.js:14` lists five page types across two locales. Home and playbook are the only marketing types. Homepage titles describe qualified inquiries on WhatsApp/Instagram; visible copy names Oman/GCC, but there are no dedicated channel, product-detail or case-study pages in the audited public set. Private dashboard routes are correctly noindex and are not substitutes for public product pages.

**Impact:** high potential, unquantified. One broad homepage has limited room to answer detailed commercial and implementation questions. This is an opportunity assessment, not a claim about current keyword rankings.

**Fix:** build a small, substantive bilingual content set around the live Catalyst scope. Validate proposed query wording against Search Console and actual search results before finalizing titles. Do not publish near-duplicate pages for every Ascend sector or imply unavailable operational features are live.

| Proposed page pair | Search-intent hypothesis | Required content and proof |
| --- | --- | --- |
| `/catalyst`, `/en/catalyst` | Arabic/English AI inquiry answering and qualification for Oman businesses | What Layla does; approved-facts workflow; qualification examples; dashboard handoff; human takeover; setup inputs; scope and billing explanation; free-audit CTA |
| `/whatsapp-automation`, `/en/whatsapp-automation` | أتمتة واتساب للأعمال في عمان / WhatsApp automation Oman | Actual supported connection path; Arabic/English example; consent and messaging constraints checked against current official docs; business readiness checklist; clear boundary between Catalyst and separately scoped outbound services |
| `/instagram-automation`, `/en/instagram-automation` | الرد الآلي على إنستغرام للأعمال / Instagram inquiry automation | Supported account/channel setup; inquiry example; qualification and handoff; limitations; link to Catalyst and audit |
| One approved case study, Arabic + English | Evidence for a relevant sector buyer | Named project and permission; actual scope; dated screenshots with permission/redaction; measured outcomes only when supported; separate non-Catalyst historical work from Catalyst proof |

Implementation must update `src/routes.ts`, route modules, `src/lib/route-seo.js`, `src/routes-manifest.js`, prerender configuration and contextual internal links together. New routes otherwise risk inheriting the current fallback **noindex** metadata. Use unique content, self-canonicals, reciprocal alternates and accurate publication/update dates. Avoid splitting channel pages until each contains enough distinct information to justify its own destination.

### C2. The playbook is a capture page with little searchable guidance — P2

**Evidence:** `/en/playbook` is titled “Three things quietly cap your growth”. Its visible content presents three broad business problems and a form; much of its roughly 1,474-character extracted text is form labels and sector options. The Arabic version follows the same structure. This is not evidence of a word-count penalty; the problem is limited visible answers to a reader's question.

**Fix:** retain the form, but publish a useful ungated excerpt: how to collect approved business facts, define qualification questions, assign the next owner action and audit unanswered inquiries. Add a concrete example, author/reviewer identity where accurate, and a descriptive title such as “WhatsApp inquiry handling checklist for Oman businesses | BznsFlow” if the final content actually fulfills that promise. Keep the existing route unless a migration has a clear benefit. Separate the downloadable guide's wider operational advice from current Catalyst product capabilities.

**Acceptance:** readers can apply at least one complete workflow without providing contact details; title/H1/description match the guide's actual subject; guide links contextually to Catalyst; both locales contain equivalent useful information. Email delivery was not tested by this audit.

### C3. Improve proof and snippet clarity without inventing claims — P3

**Evidence:** the homepage presents selected-work logos and explains the current service clearly, but the audited public pages lack detailed case studies. Homepage hero language is benefit-led (“Qualified inquiries. A clear next step.”); its supporting paragraph already names the channels. English descriptions are 176 characters on home and 182 on playbook.

**Fix:** add approved evidence close to relevant product explanations, with clear attribution and dates. Consider a concise descriptive subheading for the service category rather than stuffing the H1. Front-load each description's useful meaning; do not treat 160 characters as a hard rule. Google may generate a different snippet and truncates according to available space. Short legal-page titles already describe their pages and need no padding. [Title guidance](https://developers.google.com/search/docs/appearance/title-link), [snippet guidance](https://developers.google.com/search/docs/appearance/snippet).

The established public +20 contact is not an SEO defect simply because the target market is Oman. Do not replace it or invent an Omani office. Local listings and third-party citations require verification of the actual business and eligibility; no backlink or Business Profile conclusions were established here.

## Checks that passed and issues not to manufacture

- All 10 sitemap pages returned 200 with title, description, one H1, indexable robots and self-canonical in initial HTML. Public content does not depend entirely on client rendering.
- Sitemap and HTML hreflang pair Arabic/English and include English as `x-default`. Neither locale is canonicalized to the other.
- Tested HTTP/non-www/trailing-slash and `/ar` aliases resolved to intended canonical URLs. Redirect-chain lengths were not captured by the independent crawler.
- `/en?utm_source=seo_audit` canonicalized to clean `/en`.
- Tested sign-in, setup and dashboard pages had `noindex, follow`. Their absence from the public sitemap is intentional; the crawler's two sign-in notes are not broken-link defects.
- Both deliberately nonexistent URLs returned real 404 responses and noindex.
- HTTPS and HSTS were present. No HTTP image source was flagged in the rendered crawl; this is not an exhaustive mixed-content/security audit.
- Both homepages fit 390px without document-level horizontal overflow; Arabic used `lang=ar`, `dir=rtl`, English `lang=en`, `dir=ltr`. Mobile contact/chat controls consume visible space and should be included in later interaction testing, but no mobile indexing failure was established.
- Rendered JSON-LD on each homepage includes Organization, WebSite, SoftwareApplication, Service and FAQPage. All five blocks parse. The six English FAQ answers match the expandable page content. This is detection/content checking, not a Google Rich Results Test certification.
- **FAQ rich results are no longer shown by Google:** the current documentation records retirement beginning May 7, 2026 and removal of the documentation in June. Keeping accurate FAQPage markup is optional; adding more is not a Google rich-result opportunity. [Google documentation updates](https://developers.google.com/search/updates).
- SoftwareApplication markup lacks a public price/review combination needed for Google's software-app rich-result requirements. Do not fabricate a zero price or ratings to satisfy a validator. Generic valid schema is not a promise of a rich result. [Software-app requirements](https://developers.google.com/search/docs/appearance/structured-data/software-app).
- `og:locale=ar_AE` does not negate `hreflang=ar`; it is a social metadata alignment question, not evidence of failed Oman targeting.

## Execution order and measurement

1. **No critical indexing repair established.** Keep the working prerender, canonical, hreflang and noindex behavior intact.
2. **Small repair batch:** preview image, supporting-page links and crawlable locale links. Verify anonymous initial HTML and rendered navigation in both languages; check image status/content type. Production release remains a separate action.
3. **Performance diagnosis:** capture mobile and desktop traces, fix attributed causes, repeat comparable measurements. PageSpeed's API returned 429 in this audit, so no PageSpeed score or field pass/fail is claimed.
4. **Content batch:** publish the Catalyst explanation first, then channel pages only when distinct and useful, improve the playbook and add one approved proof page. Each new route must pass metadata, sitemap, prerender and link checks before release.
5. **Search baseline:** use Search Console to inspect the ten intended URLs, selected canonicals, sitemap processing and exclusion reasons. Export 90 days of query/page/country/device data, separate brand/non-brand and Arabic/English, then review change over time. No fixed ranking promise.
6. **Business outcome measurement:** connect organic landing pages to audit requests and qualified inquiries. Treat WhatsApp/calendar clicks as intent signals, not completed bookings or revenue. Check existing analytics events before adding duplicates. Review backlinks and relevant local citations only with actual evidence.

The 37 automated warnings should not become 37 tasks: many are image dimension ratios, short but clear legal titles, and description-length heuristics. Prioritize the confirmed missing asset, useful internal links, measured performance causes and content that answers real buyer questions.
